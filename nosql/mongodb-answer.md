# NoSQL: MongoDB

Для хранения бронирований в MongoDB я бы использовал коллекцию `bookings`, где один документ соответствует одному бронированию. Основные связи с пользователем и комнатой лучше оставить через `user_id` и `room_id`, но при этом сохранить snapshot важных данных внутри документа: имя пользователя, email, тип комнаты и цену за ночь. Это гибридный подход: referenced-связи помогают не дублировать всю сущность пользователя или комнаты, а embedded snapshot позволяет быстро проверить конкретное бронирование без дополнительных запросов.

Полностью embedding-структуру я бы не выбирал, потому что пользователь и комната могут использоваться во многих бронированиях. Если хранить их целиком в каждом документе, будет сложнее поддерживать консистентность. Snapshot при этом полезен: он фиксирует состояние данных на момент оформления бронирования, например цену комнаты.

Пример документа:

```json
{
  "_id": "booking_id",
  "user_id": "user_id",
  "room_id": "room_id",
  "user": {
    "name": "John Smith",
    "email": "john@example.com"
  },
  "room": {
    "type": "double",
    "price_per_night": 120
  },
  "checkin": "2026-06-10",
  "checkout": "2026-06-15",
  "status": "confirmed",
  "created_at": "2026-06-01T10:00:00Z"
}
```

На коллекции `bookings` я бы создал индексы по `user_id`, `room_id`, `status`, `created_at`, а также составной индекс `{ "room_id": 1, "checkin": 1, "checkout": 1 }` для проверки пересечений бронирований по одной комнате. Для отчетов и фильтрации полезен индекс `{ "status": 1, "created_at": -1 }`, потому что QA часто проверяет confirmed-бронирования за конкретный период.

Через MongoDB Compass или mongo shell я бы проверял наличие обязательных полей, корректные типы дат, допустимые значения `status`, условие `checkout > checkin`, отсутствие пересекающихся confirmed-бронирований по одной комнате и соответствие embedded snapshot актуальным данным пользователя и комнаты на момент создания бронирования.
